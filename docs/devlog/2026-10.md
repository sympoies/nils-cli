# Development log - 2026-10

## 2026-10-01 - `send` confirms a prompt left the input box

### Result

- `agent-session send` pastes text with bracketed-paste markers
  (`tmux paste-buffer -p`), so a multi-line message stays one prompt with its
  line breaks. The start-time prompt paste does the same. The web terminal
  attach input, mailbox reminders, auto-resume, and the `/rename` projection
  keep the raw paste.
- Text followed by exactly `--key enter` is a prompt submission. `send`
  presses that Enter itself, then reads the pane. If the text is still in the
  Claude Code or Codex composer 1.5 s later, it presses Enter one more time.
  It never presses while the session is `needs_input` or a dialog footer is
  shown. The whole record-lock hold, from the paste through the settle delay
  to the last pane read, is capped at 4 s, and each read is capped at the time
  remaining. A deferred provider hook event waits only 5 s for that lock. `data.submission` reports
  `{ outcome, enter_presses }`, where `outcome` is `submitted`, `queued`
  (Claude Code's "Press up to edit queued messages"), or `unverified`.
- A prompt still in the composer after the last press fails the send with
  `send-submit-stuck`, which is a non-zero exit and HTTP 409 on the serve
  route. The details include `outcome: "stuck"` and `enter_presses`, and the
  text stays in place.
- Composer recognition lives in `crates/agent-session/src/send_submit.rs`.
  Claude Code's composer is the block between the last two horizontal rules,
  starting with `❯`. Codex's composer is the last `›` block, followed only by a
  short footer. Each composer is matched on a whitespace-free probe of the
  text's first line, or on the provider's paste placeholder.

### Why / context

- Without bracketed paste, every newline reached the TUI as Enter. A message
  was either split into several prompts, or its final Enter was swallowed and
  the text stayed unsent. A long single line could also stay in the composer
  as `[Pasted text #N]`. In one session, three instructions sat unsent for
  about 80 minutes, and the sender had no signal.
- Callers such as the Telegram bridge had their own workarounds: flatten the
  text to one line, glance at the pane, and press Enter again. They can now
  rely on the `send` outcome instead.

### Evidence

- Pane captures from Claude Code 2.1.284 and Codex 0.159.0 drive the
  classifier unit tests. They cover a pending prompt, a submitted prompt, a
  paste placeholder, a startup placeholder, a queued prompt, a trust dialog,
  a Codex usage-limit dialog, and a transcript echo above an approval.
- New real-tmux integration tests drive a provider-shaped composer TUI. They
  cover multi-line ASCII and CJK for Claude and Codex, a swallowed first
  Enter, a long single line, a busy Claude queue, and a composer that never
  submits. On unmodified main they fail. With bracketed paste removed, the
  multi-line case fails because the lines are submitted separately.

## 2026-10-01 - Delivered federation envelopes no longer block remote sends

### Result

- The source federation journal (`coordination/federation-journal.json`) is
  now schema `agent-session.federation-journal.v2`. Every journal write
  compacts terminal outbox entries (`delivered`, `rejected`,
  `delivery-unknown`) into body-free `retained` records. A record is about
  0.6 KB; the live v1 entries it replaces were about 2 KB. Idempotent replay,
  reply replay, and delivery status read both lists, and identities are still
  kept until 24 hours after expiry.
- Only queued envelopes count against the send caps. The caps are 512 per
  destination machine and 2048 in total. Queued plus retained identities are
  capped at 16384. The journal limit is 32 MiB, and submit keeps 256 KiB of
  headroom by refusing with `federation-journal-bytes`.
- A retryable transport failure backs off every already-attempted queued
  envelope for the same destination session. An offline machine then costs
  one probe per destination session per retry interval and does not delay
  other destinations; a fresh envelope still gets its own first attempt.
- A v1 journal is read and rewritten as v2. Releases that only know v1 fail
  closed on a v2 journal.
- Every `quota-exceeded` site now returns details with `quota`, `count` (the
  value admission would reach), `limit`, `host`, and `side` (`source`,
  `destination`, or `local`). Source federation refusals also report pending,
  per-destination pending, delivered, and retained counts. The message ends
  with `(<quota> <count>/<limit>)`.
- The CLI keeps its local daemon's own refusal code, message, and details.
  Only relay refusals read "remote mailbox request was rejected", and they
  keep just the quota fields.

### Why / context

- One host's outbox filled with 256 already-delivered envelopes. They stayed
  until 24 hours after expiry, so every cross-host send was refused for most
  of a day. The generic CLI message made this source-side refusal look like a
  destination rejection.
- The coordinator session is moving to its own host, which makes nearly all
  of its mailbox traffic cross-host. Delivered traffic must not count against
  a send cap, and pending envelopes for a destination that goes offline (for
  example a laptop) must not block other destinations.

### Evidence

- `delivered_outbox_entries_do_not_block_new_sends` failed on the unmodified
  base with `quota-exceeded` ("remote outbox is full") and passes with the
  change.
- Observed source traffic before the fix was about 230 sends per day: 256
  entries spanned 27 hours, all with the 24-hour default expiry and 0.9 KB
  average bodies. With the 48-hour retention window that is about 460
  retained identities, roughly 0.3 MB.
- Tests also cover per-destination pending isolation, the retained-ID cap,
  the journal byte budget, per-destination backoff, destination mailbox quota
  details, and relay versus local daemon error mapping.

## 2026-10-01 - Align Codex and Claude account handling

### Result

- One account nickname rule, `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, lives in
  `nils_common::provider_runtime::accounts::is_valid_account_nickname`. The
  agent-session Codex and Claude bindings, the retitle account setting,
  `codex-cli account select`, and stored secret names all use it.
- `agent-session` has one bounded broker client (`account_broker.rs`) for both
  providers. Codex keeps the v1 protocol with no `--provider` argument, and
  Claude keeps v2. Error codes are unchanged, except that an unsafe nickname
  in a Codex broker list is now `codex-account-broker-invalid-response`.
- `PUT /sessions/{id}/account` has provider-neutral handler names. Codex now
  refuses an account the broker does not list with `codex-account-unknown`.
  An explicit `codex_account` on create is validated and must be listed before
  launch. `*-account-session-incarnation-conflict` and `*-account-unsupported`
  are HTTP 409 for both providers.
- Additive fields: `capabilities.codex_account_switch`, plus `provider` on both
  account list routes and `selection_strategies` on `/codex/accounts`.
  `serve --config` also accepts a `[claude_account_broker]` table.
- Stored names outside the nickname rule (a leading `.`, `_`, or `-`, or more
  than 64 bytes) are now ignored or rejected. This covers Claude profiles,
  `codex-cli account select` candidates, and the Codex remote secret name.
  Such profiles and secrets must be renamed; the claude-cli and codex-cli
  contract docs say where each is ignored.
- `codex-cli auth use|save|remove|refresh` declare their positional arguments
  in clap, and exit code 2 is documented.
- Rate-limit cache TTL and allow-stale parsing is shared in nils-common.
  Claude's `diag rate-limits` cache-clear hook now clears the cache.
  `diag rate-limits --all` marks the current default that `auth current`
  reports, and `auth remote pull --all --into` records it in `<dir>/.current`.

### Why / context

- The Codex daemon rule accepted `--format`, `-x`, `.`, and `..`, and those
  values reach broker argv as `resolve --account <nickname>`.
- The same account condition returned different HTTP statuses depending on
  the provider. The same broker contract was implemented twice.
- `codex-cli auth remove` still deletes the current default. The infra rename
  flow retires an alias whose identity matches the active login, and Codex
  resolves its current secret by identity. A guard like Claude's would break
  that caller.

### Evidence

- Red and green test runs for each behavior change. `cargo fmt`, `cargo clippy
  --all-targets -D warnings`, and the tests of nils-common, nils-agent-session,
  nils-codex-cli, and nils-claude-cli pass. In local-fast, only
  `serve::tests::activity_file_notification_publishes_transition_without_http_polling`
  failed, a filesystem-watcher timing test that passes when run alone.

### Result

## 2026-10-01 - Owned child sessions through Agent Console

### Result

- `agent-session start --via-console [--machine M] [--account NAME]
  [--agent-profile ID]` starts a session through Agent Console instead of
  launching tmux locally. The console owns the child for the same principal
  that owns the calling managed session, so the child shows up in that
  owner's list and board.
- The daemon route `POST /sessions/{id}/console-start/v1` authenticates the
  caller's capability. It then calls the aggregator's
  `POST /api/coordination/sessions/v1` with the relay token and the caller's
  exact identity.

### Why / context

- A dispatcher session (laoda) started workers with plain
  `agent-session start`. Those workers had no Console grant, so their owner
  could not see or attach to them, and the relay refused them. Only the
  daemon holds the relay bearer, so the CLI goes through its own daemon, as
  federated messaging does. No request field names an owner.
- `--account` maps to `codex_account` or `claude_account` so a dispatcher can
  route work to an account with remaining quota.

### Evidence

- New `board_relay.rs` console_start tests failed on the unmodified base with
  `unexpected argument '--via-console'` and pass with the change. They cover
  the forwarded body and bearer, refusal classes, disabled federation, an
  unmanaged caller, the route's capability check, and account and profile
  selection.

## 2026-10-01 - History resume keeps the conversation identity

### Result

- Archive records the managed session id and structured title state. Daemon
  history resume reuses the archived session id when it is free and restores
  the archived title and title state; resuming a Codex, Claude, or DSH
  conversation that a live managed record already owns returns
  history-session-live (HTTP 409) with that session id instead of launching a
  duplicate.

### Why / context

- Peers address sessions by agent-session id through the coordination mailbox,
  so a resume that minted a new id stranded messages and split one conversation
  into an old and a new id. The history list overlaid managed titles but the
  resume path did not, so resumed sessions started untitled and the Console
  fell back to the provider UUID. Archives from before this change have no
  session id and keep the new-id fallback.

### Evidence

- history_resume_refuses_a_conversation_a_live_session_already_owns failed
  before the change (resume went on to provider import) and
  archive_is_incarnation_fenced_and_preserves_history_metadata failed on the
  missing session_id; both pass now, with
  history_resume_restores_the_archived_session_id_only_while_it_is_free and
  resolved_archived_session_carries_its_managed_identity covering id reuse,
  fallback, and the catalog overlay.
